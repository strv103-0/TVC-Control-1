# 0001. 개발 도구 선정

- 날짜: 2026-09-02
- 상태: 채택 (2026-09-02, 시뮬레이션 항목은 Simulink로 확정)

## 배경

설계·회로·펌웨어·시뮬레이션 각 영역의 도구를 정해야 한다.
이 프로젝트에는 일반적인 경우보다 무겁게 봐야 할 제약이 두 가지 있다.

1. **데스크톱과 노트북을 git으로 오간다.** 도구가 만드는 파일이 텍스트인지 바이너리인지,
   클라우드 동기화가 되는지가 실제 작업 속도를 좌우한다.
2. **제어 보드가 미확정이다.** Teensy 4.x / STM32 / 자체 PCB 어느 쪽으로 가도
   버려지지 않는 도구를 골라야 한다.

## 결정

| 영역 | 선택 | 라이선스 |
|---|---|---|
| 기구 설계 (동체·짐벌) | Autodesk Fusion | 교육용 무료 |
| 회로·PCB | KiCad 10 | 오픈소스 |
| 펌웨어 | VS Code + PlatformIO | 오픈소스 |
| 제어 시뮬레이션 | MATLAB / Simulink | 학교 라이선스 |
| 로그 분석 | Python (pandas) + PlotJuggler | 오픈소스 |
| 신호 디버깅 | PulseView + 저가 로직 애널라이저 | 오픈소스 |
| 전원부 회로 시뮬 | LTspice | 무료 |

## 이유

### 기구 설계 — Fusion (FreeCAD 대신)

짐벌 설계의 핵심 작업은 **조인트를 걸고 가동범위 내 간섭을 확인하는 것**이다.
FreeCAD 1.1은 예전보다 크게 안정되었지만 어셈블리·조인트 작업의 안정성은 아직 Fusion 쪽이 낫다.
Fusion은 클라우드에 저장되므로 두 PC 동기화가 자동으로 된다는 점도 이 프로젝트 구조와 맞는다.

**단점과 대응**: 원본 파일이 git에 들어가지 않는다.
→ 설계가 한 단계 확정될 때마다 `hardware/cad/`에 **STEP**(형상 원본)과 **STL**(출력용)을 export 해 커밋한다.
이렇게 하면 Fusion 계정이 막히거나 도구를 바꿔도 형상은 남는다.

### 회로 — KiCad

`.kicad_sch` / `.kicad_pcb`가 텍스트 파일이라 git이 변경 이력을 제대로 추적한다.
회로도 변경 이력이 남는 것은 디버깅에서 실질적인 가치가 있다 —
"이 저항값을 언제 왜 바꿨는가"를 되짚을 수 있다.

EasyEDA는 부품 라이브러리와 JLCPCB 연동이 편하지만 클라우드 종속이고 버전 관리가 사실상 불가능하다.
KiCad에서도 JLCPCB 발주에 필요한 Gerber / BOM / CPL을 모두 생성할 수 있다.

### 펌웨어 — PlatformIO (Arduino IDE 대신)

Arduino IDE는 라이브러리를 `Documents/Arduino/libraries`에 **전역 설치**한다.
두 PC의 라이브러리 버전이 어긋나도 알 수 없고, 어긋난 채로 빌드가 통과해 버린다.
PlatformIO는 `platformio.ini`의 `lib_deps`에 버전을 명시하고 프로젝트 폴더 안에 받으므로,
git에서 clone 받은 쪽이 **같은 소스로 같은 바이너리**를 얻는다.
보드가 바뀌어도 `[env:...]` 섹션만 추가하면 되어 미확정 상태와도 잘 맞는다.

### 제어 시뮬레이션 — MATLAB / Simulink

당초 Python을 우선 검토했으나(라이선스 비용, git 친화성), **학교 라이선스 확보가 확인되어 Simulink로 정한다.**

- 비용 문제가 해소되었다.
- 블록 선도로 제어 구조를 다루는 방식 자체가 학습 목표에 부합한다.
- Simscape Multibody · Aerospace Blockset로 짐벌 다물체 동역학과 6-DOF를
  직접 구현하지 않고 얻을 수 있어, 모델 신뢰도가 자작 코드보다 높다.
- Embedded Coder로 **모델에서 보드 펌웨어까지 이어지는 경로**가 생긴다.
  이 경로가 이 프로젝트에서 배울 가치가 가장 큰 부분이다.

**감수하는 단점 1 — 라이선스 종속**: 졸업·학기 종료로 라이선스가 끊기면 모델을 열 수 없다.
→ 대응: 확정된 설계 파라미터(관성, 게인, 서보 사양)는 `.slx` 안에만 두지 말고
`docs/`에 **숫자로 기록**한다. 도구가 사라져도 결과는 남는다.

**감수하는 단점 2 — `.slx`는 바이너리**: git이 내용을 병합하지 못한다.
→ 대응: 아래 "결과" 항목의 편집 규칙을 따른다.

### Python은 버리지 않는다

로그 분석(`analysis/`)은 Python(pandas·matplotlib)으로 유지한다.
비행 로그 처리는 Simulink보다 스크립트가 빠르고, git에서 diff도 된다.

### 도구가 아닌 것: OpenRocket

"로켓"이라는 단어 때문에 후보로 떠오르기 쉬우나, OpenRocket은 화약 모터 기체의
공력 안정성(CP/CG 마진)을 계산하는 도구다.
이 기체는 공력이 아니라 **능동 제어로 자세를 유지**하므로 해석 전제가 다르다. 사용하지 않는다.

## 결과

### `.slx` 편집 규칙 (두 PC 왕복 시 필수)

Simulink 모델은 바이너리라 **양쪽 PC에서 동시에 고치면 자동 병합이 불가능**하다.
텍스트 파일처럼 다루면 반드시 사고가 난다.

1. 모델을 열기 전에 **반드시** `.	ools\sync.ps1 start`
2. 작업을 끝내면 **반드시** `.	ools\sync.ps1 end "..."` — 다음 PC로 넘어가기 전에 push
3. 한 번에 **한 PC에서만** `.slx`를 편집한다
4. 큰 구조 변경 전에는 커밋을 먼저 만들어 되돌아갈 지점을 확보한다

충돌이 나면 병합이 아니라 **어느 한쪽을 고르는 것**이 유일한 해결책이다.
(`git checkout --ours` / `--theirs`)

### 시뮬레이션은 2단계로 나눈다

1. **1축(pitch) 선형 모델** — 게인의 대략적 크기와 안정 범위를 잡는다.
2. **6-DOF 강체 + 짐벌 추력 벡터** — 축 간 커플링과 실제 실패 모드를 본다.

### 서보 모델을 반드시 비이상적으로 만든다

TVC 호버 기체가 실패하는 가장 흔한 원인은 제어 게인이 아니라 **구동기 한계**다.
시뮬레이션에 아래를 포함하지 않으면 시뮬에서 완벽한 게인이 실기에서 진동으로 발산한다.

- 서보 각속도 제한 (사양의 `0.1s/60°` 같은 값 → deg/s로 환산)
- 서보 지령~반응 지연 (수십 ms)
- 짐벌 각도 포화 (`GIMBAL_LIMIT_DEG`)
- 제어 루프 이산화 주기 (`CONTROL_HZ`)

### 보드는 2단계로 접근한다

KiCad 본격 사용은 2단계부터다.

1. **Teensy 4.1 + 브레드보드/만능기판** — 제어 알고리즘을 먼저 검증한다.
   여기서 필요한 루프 주파수와 실제 사용 핀 수가 확정된다.
2. **STM32 커스텀 PCB** — 1단계에서 나온 요구사항으로 설계한다.
   회로를 먼저 그리면 요구사항을 모르는 채로 설계하게 된다.

### Simulink 선택이 보드 선정에 미치는 영향

**Teensy 4.x는 MathWorks 공식 타겟 지원이 없다.** STM32는 ST가 제공하는 무료
Embedded Coder 지원 패키지로 Simulink에서 바로 빌드·배포된다.
코드 생성 워크플로를 쓸 계획이라면 이것이 STM32 쪽의 분명한 이점이다.

이 순서와 보드 선택은 ADR 0002(제어 보드 선정)에서 확정한다.
